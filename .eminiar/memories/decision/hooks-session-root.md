Hooks key their project on the session root (branch fix/hooks-session-root, 2026-11-08). Every hook used to call `getContext(input.cwd)`. The payload `cwd` follows Claude's `cd` (Claude Code hooks docs: "the new directory after Claude runs `cd`"), so a session started in a multi-repo folder that ran `cd backend && …` wrote its events, decisions, reindex queue, snapshots, current-session file and usage into backend's database, while the MCP server (em_search, em_recall, em_usage) kept reading the folder's. A marker-less subfolder became a project of its own. Usage double counted: the new database had no transcript offset and ingested the whole session again. After a cd, PreToolUse also stopped seeing the server's liveness marker, so enforce quietly degraded to annotate.

Decision: `sessionRoot(cwd?)` moved from src/swarm/hooks.ts to src/project.ts (same order as the 2026-10-28 swarm fix: CLAUDE_PROJECT_DIR, then EMINIAR_PROJECT_ROOT, then the given cwd, then process.cwd()), and `sessionContext(cwd)` in src/context.ts is the one context every hook handler opens. CLAUDE_PROJECT_DIR is the session's start directory and stays put across `cd`; Claude Code also sets it for stdio MCP servers, so hooks and server agree (the old "the MCP server does not receive CLAUDE_PROJECT_DIR" comments were wrong and are fixed). Cursor sets CLAUDE_PROJECT_DIR as an alias for the workspace root (Cursor hooks docs, checked 2026-11-08). The statusline prefers `workspace.project_dir` (Claude's launch directory) over `cwd` / `current_dir`; it equals CLAUDE_PROJECT_DIR unless Claude Code is given a separate project config root.

Swarm hooks take the same session context and add the cwd fallback themselves: `swarmRootCandidates(ctx, input)` and `swarmScope(ctx, input, …)` try the session root, then the root of `input.cwd` (a nested repo's own swarm, documented tracking behaviour). Callers have one context to pass, so code inside `route()` cannot hand swarm code the wrong one. Enforcement, the SessionStart text and the em_swarm stamp keep `sessionRoot()` with the process-cwd fallback: they must decide from the same directory as the no-node shim (bin/em-hook uses `$PWD`), and the fallback only matters without CLAUDE_PROJECT_DIR (CLI, tests).

Kept on the cwd on purpose: relative Bash operands (routing), the adjudicator's agent lookup, and commit hints, whose `git diff --cached -z` runs in the cwd's repository; each name (relative to that repository's top level) is re-keyed with `relative(root, join(top, name))`, which holds both for a nested repo below the session root and for a session started in a monorepo package below the git top level. The CLI, server and tools keep `resolveProjectRoot` (EMINIAR_PROJECT_ROOT first). With no CLAUDE_PROJECT_DIR (a CLI call, tests; tests/setup-env.ts deletes it) the payload cwd decides as before.

Consequence handled here: hooks of a git worktree inside the project (EnterWorktree, `isolation: worktree`) now record into the main project, so the reindex queue gets `.claude/worktrees/<n>/…` paths. `drainReindexQueue` keeps only what listCodeFiles would list: `codeFileFilter(graph)` takes fast-glob's own task patterns (`fg.generateTasks`: braces expanded, `!` includes become ignores, a `!` on an ignore is dropped) and applies fast-glob's rules with micromatch, its matcher: a positive pattern matches with dot:false, no ignore matches with dot:true, and no folder on the way matches an ignore that prunes (ends in `/**` or has a plain last segment). tests/unit/code-file-filter.test.ts checks it against a real listCodeFiles over a fixture tree for the defaults and nine custom configs. Not changed: for a `./`-prefixed include fast-glob lists `./src/a.ts`, so a full scan keys those files differently from the hooks (`src/a.ts`); the filter accepts the hook form.

Open: (1) In a multi-repo folder a repo's own memories, recall and config no longer apply after a cd; a read-side fallback (recall also searches the cwd root's database, writes stay on the session root) would mirror swarm tracking. (2) The server puts EMINIAR_PROJECT_ROOT before CLAUDE_PROJECT_DIR, so a `claude` started from Bash (which inherits the variable from the outer session's CLAUDE_ENV_FILE export) binds its server to the outer project while its hooks use their own; em_swarm stamps project_root for this, other tools do not. (3) current-session is one file per project, so two concurrent sessions in one root swap attribution in em_remember / em_execute stats; the server would need to learn its own session id.
