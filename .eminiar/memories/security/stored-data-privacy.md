What eminiar keeps on disk, and how private it is (branch fix/privacy-basics, 2026-11-08).

1. Captured output is masked at one point: indexContent (src/index/indexer.ts) runs redactSecrets() over the title, content, string meta (the intent) and any pre-cut chunks of every document whose source is exec, batch or url (em_execute, em_execute_file, em_batch_execute, em_fetch_and_index). Anything that indexes command output, stderr included, must go through indexContent with one of those sources. Files, code, git, docs (em_docs pages are documentation, where example keys are the content), memories and session documents are not touched there. What the tools show inline (small outputs, the head/tail preview, batch inline output) is as printed; sections returned for an intent or queries, and "searchable terms", come from the masked copy.
2. The short error text of a failed tool call (classify.ts errorText: first 4 KB masked, then clipped to 400) and its command summary are masked before the error event is stored; persist() indexes that event as a session document for em_recall. Still stored as written: prompts, assistant replies, subagent reports, tool-call command heads in events and hook.log, the global fetch cache (docs sync parses specs from it), documents.uri of a url (the refetch key). Masking is best effort: an opaque token alone on a line or a password in prose has no shape or name to match.
3. redactSecrets() lives in src/adjudicator/redact.ts next to redact() and reuses its RULES (see adjudicator/redact-rules), so Ryan's branches that edit that file keep merging. The hooks-off test lists redact.ts as not probed: it is pure text rules. Differences from redact(), each from measuring real output: no email/hex/base64 run rules (git SHAs, checksums, lockfile integrity, authors); no clean() (stored output keeps every character); a lone `key` keeps a value that reads as a name, path or id (under 20 chars, no digit or no letter, a dot or space, a UUID, an `algo:hex` digest, or parts between `/ _ - :` that are all under 20 chars with a plain lowercase word among them, where a long hex part may follow a `:` as in `session:<hex>`) and masks an opaque one (`live_<token>`, `prod-<token>`, `6AE843FF/INV0001A2B3…`); about 0.9% of random 32-char base64url tokens and 0.3% of alphanumeric ones still pass, mostly through the no-digit rule; a private key block ends at END within 64 KB and before the next BEGIN, else the rest of the BEGIN line and the base64 lines under it (indented or behind + > -) go; extra bare token shapes (ya29., hvs./hvb./hvr., do[por]_v1_, shp*_, pypi-, the ECR password). redact() returns exactly what it did before.
4. Output stored before masking (exec/batch/url only; old session error documents stay until a sessions purge): remaskCapturedOutput() rewrites their titles, string meta (the intent) and chunks in place, from the server warm-up after the other warm-up steps, on every start. One meta key, `captured_mask_upto` = `<CAPTURED_MASK_VERSION>:<last doc id>` (bump the version when the rules change enough), is both the resume point and the high-water mark: it is written after each slice, so a stopped server resumes (a stop between a slice and that write only redoes masked documents), and a later start goes over only the documents stored since, which catches raw output that an older eminiar still running on the same database stored after the pass (document ids are AUTOINCREMENT, never reused below the mark). Not a schema migration: those run in whichever process opens first (often a hook) and feature/jev-integrations takes v10. It works in slices (remaskDocuments, fix/remask-older-output task #69): each reads and masks documents ahead for 20 ms with no lock held (the read-ahead is kept on the adapter between slices), then writes them in one IMMEDIATE transaction that commits once 30 ms have passed (lock wait 40 ms; a busy lock throws SQLITE_BUSY and remaskCapturedOutput retries after 50 ms doubling to 2 s, 40 tries, so a second server starting together waits instead of dying; a deferred transaction failed with SQLITE_BUSY_SNAPSHOT as soon as a hook committed), and pauses 40 ms after a slice that wrote so waiting hooks get the lock. Every chunk/document write is a compare-and-set against the text it was masked from, so a row changed meanwhile is left alone; a large document spans several transactions and is written last chunk first, so a stop part-way leaves the raw start of a secret (a key's BEGIN line) for the next run, never its raw tail alone. The next-document query uses `+source` (the source index made SQLite sort every captured document after the id on each call: 106 s for the whole run on a 1.4 GB db). Each document is masked as one text rebuilt from its chunks in ord order (a code chunk's overlap lines taken once), because the chunks were cut from raw text and a private key, YAML block or .netrc pair can span them; the masked text is laid back over the chunks by line (maskAcrossChunks: unchanged lines stay, a rewritten line and the lines it swallowed go to its first line's chunk), and a chunk left empty is deleted. Changed chunks get embedded = 0 and their chunk_vec row is deleted (it was embedded from the raw text); chunks_au keeps FTS in step. Meta `remask_fts_optimize` is set in the first transaction that rewrites chunks; once no document is left, FTS5 'merge' -16 steps run on both chunk FTS tables in 30 ms IMMEDIATE transactions until a step leaves the segment structure (the %_data row id 10) unchanged, which removes the old tokens as 'optimize' would, then the mark goes (a run stopped before that leaves it for the next start). FTS5 secure-delete (what purge uses) was measured and rejected here: it does its work at COMMIT, 54–192 ms for one chunk on a 1.4 GB index, so transactions could not be kept short. PRAGMA secure_delete is on for every remask write and merge, so freed space is zeroed, and the last slice runs a best-effort wal_checkpoint PASSIVE then TRUNCATE (lock wait 0); journal_size_limit is 64 MB. Without any VACUUM, no trigram of a re-masked token is left in the file (test). Known gaps: a chunk the embedding queue is embedding while it is re-masked keeps the raw text's vector (markEmbedded does not check the body); free pages that other writers freed before the remask can still hold old text until reuse or a purge's VACUUM; content_hash and chunk hash keep their old values. Measured on the review's synthetic 1.44 GB db (50k docs, 499k chunks, 98k vectors, 3,945 rows to rewrite), a 1 ms lock poller beside it: before (2638c75) 106 s, one FTS optimize holding the lock 9.9 s, WAL left at 807 MB, and the run died on SQLITE_BUSY_SNAPSHOT the moment a hook committed; after 75 s, longest lock hold 83 ms (p99 63 ms), WAL 0 at the end. Single vec0 deletes take ~30 ms each on that db (the 1.5 MB vector blob is rewritten). Two servers on one DB split the work; a second run changes nothing.
5. Modes (POSIX): ensureDirs() creates the home 0700. An existing home is tightened (stat first, chmod only if looser than 0700, once per process) only when it is the default ~/.eminiar or holds global.db or install.json and nothing that is not eminiar's (an empty folder does not count), because EMINIAR_HOME can come from a repo's settings and be relative ("." is the project). restrictDbFiles() makes db, -wal and -shm 0600 right after every SqliteAdapter and GlobalDb open; SQLite gives the sidecars the main file's mode. Project files are never chmodded.
6. em_purge sessions also deletes the source "session" documents, which em_recall and the prompt hook recall. Exec/batch outputs carry a session_id but belong to the index scope.

Measured on M-series (this repo, 2026-11-08): redactSecrets ~30 ms/MB (44 µs for 5 KB, ~60 ms at the 2 MB cap). Lines it changes: 0/180 git log --format, 0/549 npm ls, 0/595 find, 1/6016 package-lock.json, 74/69321 src (identifiers ending in Key/pass/token followed by a type or value, and redact.ts's own comment examples), 530/222857 git log -p (mostly the redact tests' fake secrets). Hooks load redact.ts with the adjudicator off: +0.4–0.75 ms p50 on success (module load), +1.7–1.9 ms on a failed tool call's PostToolUse (first redactSecrets call), against hook budgets of seconds. Retention and size caps are a separate item.
